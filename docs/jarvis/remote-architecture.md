# JARVIS remote architecture: Vercel web + local Windows runtime

Status date: 2026-08-10. This document reflects the actual state of the code
after the additive changes below — not an aspirational target. It was
written from a sandboxed environment with no network access to the live
Supabase project and no access to the Windows host machine, so every claim
here is either (a) verified by reading/running code in this repo, or (b)
explicitly marked as requiring verification on the real machine.

## Target shape

```
Vercel (Next.js app, JARVIS_RUNTIME_ROLE=web-control-plane)
  -> Supabase Postgres (control plane: devices, agent_tasks, event_log, ...)
  -> Windows PC daemon (src/daemon, JARVIS_RUNTIME_ROLE=local-worker)
       -> Ollama (127.0.0.1:11434), Desktop Commander, Docker, browser, MCP, filesystem
```

The daemon only makes outbound HTTPS calls to the gateway (`/api/daemon/*`).
No inbound port needs to be opened on the home network for normal task
execution.

## What already existed (verified by reading the code, not assumed)

- `prisma/schema.prisma` already has `Device` and `AgentTask` models, plus
  `EventLog`, `Artifact`, `ApprovalRequest`. This is the real control-plane
  schema — no parallel `remote_tasks_v2` table was created.
- `src/daemon/` (poller, gateway client, identity, config) is already a
  separate entrypoint (`tsx src/daemon/index.ts`) from the Next.js app —
  the local/web split already exists at the process level.
- `src/app/api/daemon/*` already enforces: daemon bearer token
  (`JARVIS_DAEMON_TOKEN`, never `NEXT_PUBLIC_*`), device-binding on every
  task state transition (`task.agentId !== device.id` → 403), atomic claim
  via a conditional Prisma `update` (optimistic concurrency), and payload
  redaction on event logs.
- Frontend auth is real Supabase Auth gated to a single owner
  (`requireJarvisOwner()` in `src/lib/jarvis/owner-guard.ts`), not a stub.
- `SUPABASE_SERVICE_ROLE_KEY` is only referenced in `src/lib/env.ts` and
  `src/lib/supabase-server.ts` — both server-only, never a `"use client"`
  file. No `NEXT_PUBLIC_*` variable contains a secret (checked: `ANON_KEY`,
  `SUPABASE_URL`, `ENABLE_3D`, `ENABLE_VOICE`, `TELEGRAM_CHAT_ID`,
  `USER_HOME` — none are secrets).
- `reports/JARVIS_FULL_AUDIT_AFTER_PHASE_C.md` (2026-08-09) already ran a
  real, non-mocked audit of Phase A/B/C and voice, and honestly reported
  `FULL_AUDIT_STATUS=BLOCKED`. Its findings are treated as ground truth
  below rather than re-verified, since this pass had no way to independently
  re-run the physical/browser checks it performed.

## Real gaps found and fixed in this pass (additive, non-breaking)

| Gap | Fix | File(s) |
|---|---|---|
| No device targeting on tasks | `AgentTask.targetDeviceId` (nullable — `null` = any device, current single-device behavior unchanged) | `prisma/schema.prisma`, migration `20260810000000_remote_control_plane_protocol` |
| No task lease: a claimed task with a dead daemon stayed `claimed`/`running` forever | `AgentTask.leaseExpiresAt`; claim route reclaims expired leases; every `TASK_*` event renews the lease (proves the worker is alive) | `src/app/api/daemon/tasks/claim/route.ts`, `src/app/api/daemon/tasks/[id]/events/route.ts` |
| No task idempotency key | `AgentTask.idempotencyKey` (unique, nullable) — available for whoever creates remote-command tasks; not yet wired into a creation endpoint (see "Not done" below) | `prisma/schema.prisma` |
| Device online/offline was never computed anywhere — `Device.status` is only ever written to `"online"` by heartbeat/register, nothing ever flips it back | `GET /api/devices/status`: owner-authenticated, computes `ONLINE`/`OFFLINE`/`DISABLED` from `lastHeartbeatAt` freshness (90s = 3x default heartbeat interval) on every read, no cron needed | `src/app/api/devices/status/route.ts` |
| Topbar hardcoded a static green "ONLINE" badge — always claimed online even if the daemon had never run | Real client component polling `/api/devices/status` every 20s | `src/components/layout/device-status-badge.tsx`, `src/components/layout/topbar.tsx` |

## `check:runtime-boundary` result (this pass)

```
npm run check:runtime-boundary
VERCEL_LOCAL_IMPORT_VIOLATIONS=73
```

73 real call sites across 20 files under `src/app`, `src/lib`, `src/services`
that reach `child_process`, `127.0.0.1:11434`, Desktop Commander, or a
Windows absolute path directly, from code that `next build` would bundle if
this app were deployed to Vercel as-is today. Full list: run the script.
Notable ones: `src/app/api/jarvis/ollama/route.ts`,
`src/app/api/os/open-file-manager/route.ts`, `src/app/api/terminal/exec/route.ts`,
`src/lib/worker-registry/adapters/{claude-code,codex-cli,antigravity-cli}.ts`,
`src/lib/tool-hub/adapters/{git,project}.ts`, `src/services/graphify.service.ts`.

**This was not fixed in this pass.** Moving 73 call sites behind
`JARVIS_RUNTIME_ROLE !== "web-control-plane"` guards (or behind the daemon
task/capability system) is a real, substantial piece of work, and several of
these (the worker-registry CLI adapters, the terminal executor) are exactly
the code the existing Phase A/B/C baseline depends on. Doing this blind, in
a sandbox with no way to run the dev server or the full test suite against a
live database, risks regressing a baseline that took the prior sessions
weeks to get to a real, audited PASS. The scanner exists so this is a
trackable, re-runnable metric instead of a one-time guess — re-run it after
each batch of routes is migrated.

## Not done in this pass (needs the real machine, or is out of scope for a sandbox)

- **Voice E2E.** `reports/JARVIS_FULL_AUDIT_AFTER_PHASE_C.md` already found
  this broken independently of the Vercel migration (no physical mic
  detected, voice commands never reach real capability execution, TTS is
  Russian-only). Nothing in this pass touched the voice pipeline. Fixing it
  requires a live browser + microphone on the Windows machine.
- **Wiring `/api/daemon/tasks/claim` execution to real local capabilities**
  (Ollama, Desktop Commander, MCP, browser) for *remote-command* tasks — the
  daemon's `executeTask` currently only understands mock commands (`NOOP`,
  `WRITE_TEST_ARTIFACT`, `HEALTH_CHECK`, `READ_METADATA`) plus a generic
  `ExecutionPlan` step-runner for the multi-agent orchestrator. There is no
  existing "chat/voice message → remote AgentTask → daemon executes it →
  result streams back to the browser" path yet. Building one honestly is a
  significant feature, not a patch, and this pass deliberately did not
  attempt it blind.
- **Windows Task Scheduler autostart, daemon restart/offline/reconnect E2E,
  live Ollama/MCP/Desktop Commander E2E, Vercel deployment.** All require
  presence on the actual Windows machine and/or a live Vercel/Supabase
  project session; none are reachable from this sandbox. See
  `REMOTE_SETUP_WINDOWS_VERCEL.md` for exact commands to run locally.
- **The 73 runtime-boundary violations above.**
- **RLS policies.** Not independently re-audited here; `docs/jarvis/phase-b-security.md`
  and `reports/JARVIS_PHASE_C_SECURITY_REVIEW.md` cover the existing posture.
  No new tables were added that need new RLS (the migration only added
  columns to already-covered tables).
